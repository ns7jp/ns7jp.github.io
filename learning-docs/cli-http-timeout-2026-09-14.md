# 接続タイムアウトと正常応答の切り分け

実施日：2026年9月14日（JST）

本人がWSL Ubuntuで既存のcheck-http-body.shを使い、ローカルの18081番ポートへの接続失敗と80番ポートの正常応答を確認しました。AIが手順を案内し、本人が提示した端末画像を読み取って公開用要約を作成しています。AIの代理実行やCIの実測ではありません。

[本文判定スクリプト](./cli-http-body-check-2026-09-14.md)の追加試験です。既存スクリプトは変更せず、nginxの停止や設定変更も行っていません。

## 本人が実施した確認

| 段階 | 操作 | 提示画面で確認した結果 |
| --- | --- | --- |
| スクリプト検索 | findでcheck-http-body.shを検索 | 1件を表示、終了コード0 |
| 待受確認 | ss -lntで18081番を絞り込み | 見出しのみ、終了コード0。確認時点でTCP待受表示なし |

## 想定と実際の結果

事前には接続失敗の終了コード7を想定していましたが、実際は約10秒でタイムアウトし28でした。予想に合わせて7と記録せず、実際の出力を残しています。HTTP表示000はサーバーから返ったステータスではなく、HTTP応答を受け取れなかったときのcurlの表示です。

待受一覧に表示がないことだけで、接続が直ちに拒否されるとは限りません。ただし、今回タイムアウトした理由について、ファイアウォールやWSLのネットワーク構成を調査したわけではありません。具体的な原因は未特定です。

続けて80番への接続ではHTTP 200と期待する文字列を取得できました。18081番の結果を根拠にnginx全体が停止したとは判断しません。一方、80番の成功も、他のポートや別端末からの到達性を保証しません。

[過去のHTTP 404試験](./cli-http-404-2026-09-14.md)ではサーバーから404の応答を受け取っていました。今回は18081番でHTTP応答自体を受け取れず、失敗の段階が異なります。今回404を再試験したという意味ではありません。
