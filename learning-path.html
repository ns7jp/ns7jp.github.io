始める前に準備教材8段階障害演習修了判定用語集成果物を見る
所要目安 12〜20時間／自分のPC内の検証環境

読むだけでなく、「予想する → 実行する → 証拠を残す → 説明する」

このページは成果物を見る順番ではなく、未経験者が手を動かす順番です。各段階は、目的・前提・操作・期待結果・失敗例・合格条件を同じ型で確認します。分からない言葉は一言用語集へ戻ります。冒頭の所要目安12〜20時間は「8段階の学習ルート」本編8つの合計時間で、下の準備教材（環境構築・最初の30分・困ったとき・提出前レビュー）に使う時間は含みません。

安全ルール（学習者が必ず守ること）

個人PC内のVMまたはWSL2で実施します。職場・学校・第三者のサーバーでは実行しません。削除・Firewall・SSH変更の前にスナップショットと戻し方を確認します。パスワード、秘密鍵、トークンはコマンド行や公開ログへ書きません。

このコースの実測範囲（NOT RUN）

AWS、Slack実通知、72時間連続試験、別ホスト復元は手順設計済みですが、このリポジトリでは未実測（NOT RUN）です。実施した範囲だけ状態を変更し、各Stepの証跡でMEASUREDとNOT RUNを区別します。

8段階の学習ルート

STEP 0／30分未着手

環境と安全を確認

前提: 環境準備ガイド完了。一般ユーザー、8GB以上の空き、削除方法。

必要・影響: OS・容量・IP・Git。変更なし。

目的: 壊してよい範囲を決める。

操作: OS、容量、IP、Git状態を採録。例: bash scripts/capture-lab-evidence.sh preflight（Step 0の詳細手順）

期待: 環境情報ファイルが作られる。

失敗例: 実機とVMの取り違え。

合格: 削除方法と秘密情報の扱いを説明できる。

STEP 1／60分未着手

要件と構成を決める

前提: Step 0合格。用語集のIP、Port、RTO/RPO。

必要・影響: 文書編集のみ。管理者権限・通信不要。

目的: 作業前に完成条件を決める。

操作: 利用者、通信、RTO/RPO、除外範囲を記入。（Step 1の記入項目）

期待: 要件と構成図が対応する。

失敗例: 技術名だけで目的がない。

合格: 「誰が何のために使うか」を1分で説明できる。

STEP 2／90分未着手

最小OSを準備

前提: Step 1合格。Ubuntu VM、snapshot、console経路。

必要・影響: ネット接続と管理者操作あり。SSH変更前に別経路を維持。

目的: 初期状態を再現する。

操作: Ubuntu VM、一般ユーザー、SSH、更新を準備。例: ssh -i ~/.ssh/lab_key student@192.0.2.10（Step 2の詳細手順）

期待: 管理端末から鍵で接続できる。

失敗例: SSH変更後に接続不能。

合格: 再起動後も接続でき、バージョンを記録できる。

STEP 3／2時間未着手

手動で最小構築

前提: Step 2合格。Package、Service、Port、Firewallを用語集で確認。

必要・影響: Docker導入とFirewall変更あり。snapshotから戻せること。

目的: 自動化の前に構成を理解する。

操作: Docker、Webサービス、Firewallを設定。例: ss -lntpで待受portを確認（Step 3の詳細手順）

期待: 許可した経路だけ応答する。

失敗例: ポート公開と待受の混同。

合格: 通信経路とログ位置を図で説明できる。

STEP 4／2時間未着手

Ansibleで再構築

前提: Step 3合格。Git差分とYAMLの基本を確認。

必要・影響: Ansibleが必要。syntax-checkとcheckをapplyより先に実行。

目的: 人による手順差を減らす。

操作: syntax-check、check、applyを順に実行。例: ansible-playbook ansible/playbook.yml --check --diff（Step 4の詳細手順）

期待: 2回目は不要な変更が0。

失敗例: 変数未定義、権限不足。

合格: changed=0と差分を証跡に残せる。

STEP 5／2時間未着手

監視と通知を確認

前提: Step 4合格。Metrics、Logs、Alert、Runbookを確認。

必要・影響: Docker Compose構成が必要。通知先はローカルのみ。

目的: 利用者より先に異常へ気付く。

操作: メトリクス、ログ、ローカル通知を確認。例: docker compose up -dで監視スタックを起動（Step 5の詳細手順）

期待: 発生時刻と復旧時刻が追える。

失敗例: 監視自身の停止を見逃す。

合格: アラートからRunbookへ移動できる。

STEP 6／3時間未着手

障害を切り分ける

前提: Step 5の正常値を採録済み。障害演習の共通ルールを確認。

必要・影響: 管理者操作あり。1回に1つだけ壊し、中止条件を先に記録。

目的: 勘ではなく事実で原因を狭める。

操作: 仮説、確認、結果、次の判断を記録。例: journalctl -u nginx -n 50で直近ログを確認（Step 6の詳細手順）

期待: 復旧前後の証拠が残る。

失敗例: 記録前に再起動する。

合格: 原因と再発防止を第三者へ説明できる。

STEP 7／3時間未着手

復元して引き渡す

前提: Step 6合格。backup、checksum、RTO/RPOを確認。

必要・影響: 新規VMと十分な空きが必要。元データを変更しない。

目的: バックアップが使えることを確かめる。

操作: 復元、整合性確認、RTO/RPO採録。例: sha256sum backup.tar.gzで整合性確認（Step 7の詳細手順）

期待: 手順だけで再現できる。

失敗例: バックアップ取得だけで終了。

合格: 結果票、残課題、切り戻しを引き渡せる。

正常系の後に行う8つの障害演習

障害、最初の確認、完了条件
障害最初の確認完了条件
SSH接続不可IP → 経路 → TCP/22 → Firewall → sshd遮断箇所を特定し別セッションで復旧
Web応答なしDNS → TCP → Proxy → App → DB依存関係ごとに合否を記録
ディスク逼迫df（ディスク使用率を表示） → inode（ファイル管理情報の残数） → du（ディレクトリ配下の使用量を集計） → ログ削除前に原因と保持要件を確認
CPU高騰uptime（稼働時間と負荷平均を表示） → top（プロセスごとのCPU/メモリ使用率をリアルタイム表示） → ps（実行中プロセスの一覧） → ログ対象プロセスと発生時刻を特定
メモリ不足free（空きメモリ量を表示） → ps → journal/OOM（メモリ不足によるプロセス強制終了）再起動だけに頼らず原因を記録
設定破損構文検査 → Git差分 → 直前変更修正または切り戻しを選択
TLS期限異常名前解決 → 時刻 → 証明書期限・SAN更新手順と監視閾値を説明
バックアップ破損サイズ → checksum → 展開 → 復元代替世代を選び整合性を確認
