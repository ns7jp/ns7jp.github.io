Nginx Stop & Recovery Drillnginxを止めて戻す切り分け練習

初心者向け学習ルート インフラ用語集 Linux基本確認 Linuxコマンド nginx停止の練習 動作確認の記録
障害対応の練習 / Ubuntu・Docker Compose

「Webが表示されない」を、自分で起こして自分で戻す

障害対応は、本番で初めて経験すると焦ります。そこで、自分専用の練習環境で入口のnginxだけを止め、どこに何が表れるかを先に知っておきます。見るのは状態・応答・ログの3点です。最後に元へ戻し、4行の記録を書いて終わります。

この練習でできるようになること「nginxが止まっていて、appは動いている」と、コマンドの表示を根拠に説明できるようになります。curlが000を返したときに、何が起きているかも読めるようになります。

合格の目安

(1) 止める前・止めた後・戻した後の3回分の表示を保存している。(2) 止めた後の000と、戻した後の200の違いを自分の言葉で言える。(3) 4行の記録を、自分の結果で埋められる。

安全な練習場所

自分専用のVM（パソコンの中に作るもう1台のコンピューター）かWSL2で行います。会社・学校・公開中のサーバーでは行いません。環境がまだなければ、先に主作品の初回手順で、appとnginxの2サービスを起動できる状態にしてください。

このページの元になった記録と、その範囲

手順と表示例は、2026年10月1日の演習記録をもとにしています。手元のHyper-V上のUbuntu 24.04系の仮想マシンで、AIの手順案内を受けて本人が操作しました。復旧は手動の起動で、自動復旧の確認ではありません。AIの案内なしでの再現、監視通知、長時間の稼働は、この記録には含まれていません。

以下の操作例は、主作品の初回手順で用意する構成に合わせています。元の演習記録とはプロジェクト名やログの設定が異なる場合があるため、今回の結果は自分の環境で確かめて記録してください。

手順1. 構成をつかむ2. 正常時を記録3. nginxを止める4. 3点で確かめる5. 元に戻す6. 4行で記録7. curlの読み方8. 応用問題

1. 構成をつかむ：要求はどこを通るか

かんたんに言うとブラウザやcurlからの要求は、まず入口のnginxに届きます。nginxは要求を奥のappへ渡し、appが作った返事を返します。nginxが止まると、appが元気でも外からは届きません。

流れ：curl → nginx（入口・8080番） → app（返事を作る） 入口が閉じると、奥が動いていても「つながらない」になります。

この練習で使う確認先は2つです。/healthzは「動いているか」だけを返す確認用の場所で、正常なら200が返ります。トップの/はパスワード（Basic認証）が必要なので、認証なしで開くと401が返ります。401は故障ではなく、想定どおりの結果です。

2. 止める前に、正常時の表示を記録する

壊す前の姿を残しておかないと、後で「戻った」と言い切れません。初回手順で起動したときと同じserverディレクトリ（compose.yamlがある場所）・設定で、次の3つを上から順に実行し、表示をメモかファイルに保存します。初回手順ではcompose.yamlのプロジェクト名server-monitor-labを使うので、以下のコマンドに-pは付けません。

独自のプロジェクト名を-pや環境変数で指定して起動した場合だけ、そのときと同じ指定を、この後のすべてのdocker composeコマンドでも使ってください。最初の状態確認でappとnginxが出ない場合は、停止操作に進まず、起動時のディレクトリ・設定・プロジェクト名を確認します。

compose ps参照

2つのサービスの状態を見る

$ docker compose ps --all app nginx

期待：appがUp (healthy)、nginxがUp。--allを付けると、止まったサービスも一覧に残ります。

curl通信

入口から応答を確かめる

$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/healthz
200

読む：-o /dev/nullで本文を捨て、-w '%{http_code}'で数字だけを表示します。200なら正常です。

curl / compose logs通信・参照

ログに残る要求を送り、直近の記録を見る

$ date -u '+%Y-%m-%dT%H:%M:%SZ'
$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/
401
$ docker compose logs --timestamps --tail=20 nginx

読む：この構成では/healthzのアクセスログを抑止しています。ログ確認には認証なしの/への要求を使います。date -uで記録したUTC時刻と、--timestampsで各ログ行に付くUTC時刻（末尾がZ）を比べます。今回の新しいGET /と401のアクセス記録があれば、要求がnginxまで届いた証拠です。以前の行だけで判断しません。

3. nginxだけを止める

止めるのはnginxだけです。appには触れません。「どこを止めたか」が1か所に決まっていると、後の観察で原因と結果を結びつけやすくなります。

compose stop停止

nginxを止める

$ date -u '+%Y-%m-%dT%H:%M:%SZ'
$ docker compose stop nginx

ポイント：止める直前にdate -uでUTC時刻を残します。ログと照らし合わせるときの目印になります。downは箱ごと消すので、この練習では使いません。

4. 状態・応答・ログの3点で確かめる

かんたんに言うと1つの表示だけで判断しません。「状態は止まっている」「応答は返らない」「同じ要求を送っても新しいアクセス記録が増えない」の3点を合わせて、nginxが止まっていることを確かめます。

状態参照

nginxはExited、appはUp

$ docker compose ps --all app nginx

期待：nginxがExited (0)、appはUp (healthy)のまま。(0)は「正常に終了した」という終了コードで、自分で止めたときの値です。異常終了なら0以外の数字になります。

応答通信

curlが000を返す

$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/healthz
curl: (7) Failed to connect to 127.0.0.1 port 8080 ...
000
$ echo $?
7

読む：000はHTTPの返事が1つも来なかったという意味です。(7)は「接続できなかった」を表すcurlの終了コードで、8080番の受付口が閉じていることを示します。

ログ通信・参照

同じ要求のアクセス記録が増えないことを見る

$ date -u '+%Y-%m-%dT%H:%M:%SZ'
$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/
curl: (7) Failed to connect to 127.0.0.1 port 8080 ...
000
$ echo $?
7
$ docker compose logs --timestamps --tail=20 nginx

読む：手順2と同じ/への要求もnginxに届かないため、今回のUTC時刻に対応する新しいGET /のアクセス記録は増えません。停止処理のメッセージや過去のアクセス記録とは区別し、状態・応答の結果と合わせて判断します。

5. 元に戻して、戻ったことを確かめる

起動しただけでは「戻った」とは言えません。手順2と同じ3つを実行し、止める前の表示と比べます。

compose start起動

nginxを起動する

$ docker compose start nginx
$ docker compose ps --all app nginx

期待：nginxがUpに戻り、appはUp (healthy)のまま。

curl通信

200が返ることを確かめる

$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/healthz
200

比べる：手順2と同じ200が返ることを確かめます。/healthzはアクセスログに残らないため、ログは次の/への要求で確認します。

curl / compose logs通信・参照

復旧後のアクセス記録を確かめる

$ date -u '+%Y-%m-%dT%H:%M:%SZ'
$ curl --max-time 10 -sS -o /dev/null \
    -w '%{http_code}\n' http://127.0.0.1:8080/
401
$ docker compose logs --timestamps --tail=20 nginx

比べる：認証なしの/が401を返し、ログ行に付いたUTC時刻で今回の新しいGET /と401のアクセス記録が増えたことを確認します。状態・応答・ログの3点が手順2とそろえば、戻ったと判断できます。

6. 4行で記録する

練習は記録を書いて終わりです。学習ルートの「4行の記録」と同じ形で、自分の結果を埋めます。下は書き方の例です。

  1. 目的nginxが止まったとき、どこに何が表れるかを確かめる何のためにやったかを1行で書きます。
  2. 操作compose stop nginx → ps / curl / logs → compose start nginx実行した順番どおりに書きます。
  3. 根拠停止中: Exited (0)・curl 000 (exit 7)・今回のアクセス記録なし／復旧後: Up・/healthz 200・/ 401の新規アクセス記録自分の画面に出た値と時刻を、そのまま写します。
  4. 未実施自動復旧、監視からの通知、OS再起動後の確認やっていないことを書くと、記録の信頼性が上がります。

7. curlの結果の読み方早見表

同じ「表示されない」でも、curlの結果で疑う場所が変わります。数字は一律の正解ではなく、次に見る場所を決めるための目安です。

curlの結果と、その意味、次に確かめること
curlの結果 意味 次に確かめること
200正常に返事が来たなし。比較用に記録だけ残す
401認証が必要（この構成のトップページでは想定どおり）認証情報を付けたときに200になるか
502 / 504入口は動いているが、奥のappから返事がないappの状態とログ
000（終了コード7）受付口に接続できない入口のサービスが止まっていないか、ポート番号は合っているか
000（終了コード28）時間内に返事がない（タイムアウト）経路やファイアウォール、相手が重くなっていないか

終了コードは、curlの直後にecho $?で表示できます。ネットワークの確認方法はLinuxの基本確認の「通」と「壁」も参考にしてください。

8. 応用問題

答えを見る前に、予想を書いてから試します。予想と結果が違ったときこそ、構成の理解が深まります。

理解度チェック（答えを見る）
Q1. nginxを止めた後、appも止まったと判断してよいですか？
いいえ。psでappはUp (healthy)のままです。入口が閉じているだけなので、1つの表示だけで判断しないことが大切です。
Q2. 認証なしで/を開いて401が返りました。障害ですか？
いいえ。この構成ではトップページにBasic認証がかかっているため、想定どおりです。正しい認証情報を付けて200になるかで確かめます。
Q3. 今度はnginxではなくappを止めたら、curlの結果はどう変わると思いますか？
入口のnginxは動いているので、受付口への接続はできるはずです。そのうえで、奥から返事がないことを示す502などに変わると予想できます。実際の値は自分の環境で試して記録してください。終わったら必ずstart appで戻します。
Q4. 練習の最後にdownではなくstopを使ったのはなぜですか？
downはコンテナやネットワークを削除します。この練習の目的は「止めて戻す」なので、削除を伴わないstopとstartで十分です。

次の学習へ

止める・確かめる・戻すの流れに慣れたら、問い合わせを想定した「重・空・動・記・通・入・壁」の確認順へ進みます。
