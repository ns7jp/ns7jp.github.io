# 成果物テンプレートと完成例

このページには、学習の記録を残すための記入用ひな形（テンプレート）と、その記入例をまとめています。書き方をそろえておくと、後から自分でも他人でも読み返せます。

実際に使っているIPアドレス（機器に割り当てられた住所にあたる番号）、ホスト名（機器につけた名前）、利用者名、パスワードなどの秘密情報は記入しません。空欄は推測で埋めません。まだ実行していない項目は `NOT RUN`、確かめられていない項目は `未確認` と書きます。

## 1. 要件・構成メモ

> **かんたんに言うと** 作り始める前に「何のために・誰のために作るのか」と「どこまでやるのか」を1枚に書き出すメモです。

最初にこれを書いておくと、作業中に迷ったときの判断基準になります。面接でも「なぜこの構成にしたのか」「何を対象外にしたのか」を自分の言葉で説明できます。

### 空テンプレート

```text
目的 / 利用者:
成功条件:
対象 / 対象外:
接続元 → 宛先 → protocol/port:
データ / backup:
許容停止時間(RTO) / 許容損失(RPO):
前提 / リスク / 戻し方:
```

各項目の読み方は次のとおりです。`protocol/port` は通信の種類（プロトコル）と、受け口の番号（ポート番号）を指します。`backup` はデータの控えを取ることです。`RTO` は Recovery Time Objective の略で、復旧までにかけてよい時間の目標です。`RPO` は Recovery Point Objective の略で、失ってもよいデータの時間幅を表します。

### 合格水準の架空例

以下は書き方の見本として作った架空の記入内容です。実際に構築して確かめた結果ではありません。

```text
目的 / 利用者: 学習者が管理端末からLab Webの状態を確認する
成功条件: 管理元だけSSH、clientからHTTPS、異常を5分以内にローカル検知
対象 / 対象外: Ubuntu VMとLab container / 公開DNS・本番通信は対象外
接続元 → 宛先 → protocol/port: admin → VM → TCP/22、client → proxy → TCP/443
データ / backup: 設定とtest dataを日次保存、checksumを確認
RTO / RPO: 60分 / 24時間（目標。別host実測はNOT RUN）
前提 / リスク / 戻し方: NAT内、snapshot取得、consoleからrollback
```

この例では「目的、通信、対象外、目標、戻し方」の5つが書かれています。しかも、それぞれが後で行う試験項目までたどれる形になっています。ここでの「たどれる」とは、要件の1行を読めば、それを確かめる試験がどれか分かる状態のことです。そのため設計区分12点相当です。以下に16点・20点相当の架空の記入例を示します。

### 16点相当の架空例

```text
目的 / 利用者: 学習者が管理端末からLab Webの状態を確認し、障害を自分で切り分けられるようにする
成功条件: 管理元だけSSH、clientからHTTPS、異常を5分以内にローカル検知、切り分け手順で原因箇所まで特定できる
対象 / 対象外: Ubuntu VMとLab container、監視・alert経路 / 公開DNS・本番通信・複数VM構成は対象外
接続元 → 宛先 → protocol/port: admin → VM → TCP/22、client → proxy → TCP/443、monitor → exporter → TCP/9100（各通信をfailure-drills.mdの該当drillへ対応付け）
データ / backup: 設定とtest dataを日次保存、checksumを確認、復元手順書へ追跡できる
RTO / RPO: 60分 / 24時間（目標。別host実測はNOT RUN。lab-guide.md Step7で実施予定）
前提 / リスク / 戻し方: NAT内、snapshot取得、consoleからrollback、各リスクの試験項目をsecurity-threat-model.mdへ記載
```

この例（架空の記入例）では、要件の1行ごとに、それを確かめる試験手順まで書き足しています。12点相当の例との違いは2つです。1つは監視の経路を対象に加えたこと、もう1つは各項目をfailure-drills.mdやsecurity-threat-model.mdなど試験を書いた文書へ結び付けたことです。そのため設計区分16点相当です。

### 20点相当の架空例

```text
目的 / 利用者: 学習者が管理端末からLab Webの状態を確認し、障害を自分で切り分けて復旧できるようにする
成功条件: 管理元だけSSH、clientからHTTPS、異常を5分以内にローカル検知、非機能要件（可用性・性能の目標値）を明記し達成有無を判定できる
対象 / 対象外: Ubuntu VMとLab container、監視・alert経路、脅威モデルの主要リスク / 公開DNS・本番通信・複数VM構成は対象外（理由: 個人検証環境のため）
接続元 → 宛先 → protocol/port: admin → VM → TCP/22、client → proxy → TCP/443、monitor → exporter → TCP/9100（security-threat-model.mdの通信フロー表と対応、各行の脅威・軽減策・受容理由を記載）
データ / backup: 設定とtest dataを日次保存、checksumを確認、暗号化方式と鍵の保管場所を明記、復元試験の合否まで追跡
RTO / RPO: 60分 / 24時間（目標として明記。別host実測はNOT RUN、lab-guide.md Step7で実施予定）
前提 / リスク / 戻し方: NAT内、snapshot取得、consoleからrollback。各リスクについて受容・軽減・移転・回避のどれを選んだか理由付きで記載
```

この例（架空の記入例）は、非機能要件（速さや止まりにくさなど、機能そのもの以外に求める条件）と、脅威ごとにどう判断したかの理由まで書いています。そのため設計区分20点相当です。ここまでの例はいずれも架空の記入例であり、実際に検証した結果ではありません。

## 2. 作業・確認記録

> **かんたんに言うと** 「いつ・誰が・何を変えて、その結果どうなったか」を1件ずつ残す作業日誌です。

設定を変えるたびにこの形で記録します。後で問題が起きたとき、どの変更が原因かをたどれるようにするためです。面接や報告では「変更前に戻す手段を用意したうえで作業し、結果を別の方法でも確認した」と説明できます。

```text
日時 / 実施者 / 環境 / commit:
変更目的 / 対象 / 承認:
事前状態 / backup / rollback:
実行コマンド:
期待結果:
実際の結果 / exit code:
変更後の別手段での確認:
判定: PASS / FAIL / NOT RUN
証跡の保存先 / 秘密情報確認:
```

用語の意味は次のとおりです。`commit` は変更を記録した時点につく識別子です。`exit code` はコマンドが終わったときに返る番号で、0が成功、それ以外は失敗を表します。`証跡` は結果を後から確認できるように残したファイルです。判定は `PASS`（合格）、`FAIL`（不合格）、`NOT RUN`（実行していない）の3つから選びます。

## 3. 障害記録

> **かんたんに言うと** システムが正しく動かなくなったとき（障害）に、その経過と原因を書き残すための形式です。

慌てて直す前に、見えている事実と自分の推測を分けて書きます。分けて書くと原因を取り違えにくくなり、後から「どう切り分けたか」を順を追って説明できます。

```text
検知時刻 / 着手 / 復旧:
現象 / 利用者影響 / 直前変更:
事実 / 推測 / 未確認:
仮説 → 確認 → 結果 → 次の判断:
原因 / 暫定復旧 / 恒久対策:
実測RTO / RPO / 残課題:
```

`暫定復旧` は、とりあえず使える状態へ戻すことです。`恒久対策` は、同じ障害が再び起きないようにする対策です。`実測RTO` は実際に復旧までかかった時間、`RPO` は失ったデータの時間幅で、どちらも計測した値だけを書きます。計測していない場合は `NOT RUN` と書きます。

## 4. 引き渡し報告

作った環境を他の人へ引き継ぐとき、「どこまで終わっていて、何が残っているか」を隠さず伝えるための形式です。引き継いだ人が同じ手順を再現でき、異常が出ても自分で対処できる状態にすることが目的です。

```text
完了した範囲:
受入試験と結果:
日常確認 / alert時のRunbook:
backup / restore結果:
未実施(NOT RUN) / 既知の制約:
rollback / 緊急連絡:
廃棄する環境と期限:
```

用語の意味は次のとおりです。`受入試験` は、引き継ぐ人が「確かに動く」と確かめるための試験です。`alert` は異常を知らせる通知、`Runbook` は通知が出たときに何をするかを状況別にまとめた手順書です。`restore` は控えから元の状態へ戻すこと、`rollback` は変更前の状態へ戻すことを指します。

## 自己採点

[修了判定ルーブリック](./assessment-rubric.md)（区分ごとの採点基準をまとめた表）と自分の成果物を照らし合わせ、各区分の点数を自分で付けます。このとき点数だけでなく、その点数の根拠になるファイルを1つ以上記載します。根拠ファイルとは、実際に実行した記録や証跡が入っているファイルのことです。完成例をコピーしただけの項目や未実施項目は加点しません。
