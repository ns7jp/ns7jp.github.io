# HTTP確認とログ保存のスクリプト化

実施日：2026年9月14日（JST）

本人がWSL Ubuntuでrun-http-check.shを作成し、既存の本文確認処理を呼び出して日時・出力・終了コードをログへ追記する動作を確認しました。AIが手順を案内し、本人が提示した端末画像を読み取って公開用要約を作成しています。AIの代理実行やCIによる実測ではありません。

[本文判定スクリプト](./cli-http-body-check-2026-09-14.md)と[手動でのログ保存](./cli-http-run-log-2026-09-14.md)を組み合わせた追加演習です。定期実行や自動通知はまだ設定していません。

## 作成した処理

次は会話で案内し、保存操作の画面で確認したコードです。ローカル原本の取得・ハッシュ照合は行っていません。

```bash
#!/usr/bin/env bash

if [ "$#" -lt 2 ] || [ "$#" -gt 4 ]; then
  echo "使い方：bash run-http-check.sh 確認スクリプト ログ [URL] [期待文字列]" >&2
  exit 125
fi

checker="$1"
log_file="$2"
url="${3:-http://127.0.0.1/}"
expected="${4:-Welcome to nginx!}"

if [ ! -f "$checker" ] || [ ! -r "$checker" ]; then
  echo "確認スクリプトを読み取れません" >&2
  exit 125
fi

exec 3>> "$log_file" || exit 125
started_at=$(date -Is) || exit 125
printf '\n=== HTTP確認 ===\n開始日時=%s\n' "$started_at" >&3 || exit 125

bash "$checker" "$url" "$expected" >&3 2>&1
check_status=$?

printf 'スクリプト終了コード=%s\n' "$check_status" >&3 || exit 125
exec 3>&-
echo "確認結果=$check_status ログ=$log_file"
exit "$check_status"
```

出力先3をログへ追記用に開き、本文確認処理の標準出力と標準エラーを同じログへ送ります。確認処理の直後に終了コードを保存し、ログへ追記した後、その値を実行用スクリプトから返します。

125は引数・確認スクリプトの読み取り・ログ準備などのエラー用に定義していますが、今回その経路は試験していません。あらゆる書き込み失敗を検出する保証はなく、実行中の出力失敗やファイルのクローズ失敗などは未検証です。

## 本人が実施した結果

確認スクリプトの検索・作業先作成・ファイル保存・bash -nの構文確認は終了コード0でした。本人が同じhistory.logを指定して3回、bash経由で手動実行しました。

| 条件 | ログで確認した内容 | 実行用スクリプトの終了コード |
| --- | --- | --- |
| 正常URL・既定の期待文字列 | 開始日時、HTTP 200、Welcome to nginx!を含む本文の行、成功、確認処理の終了コード0 | 0 |
| 同じURL・存在しない期待文字列 | 開始日時、HTTP 200、本文確認失敗、確認処理の終了コード1 | 1 |
| 存在しないURL | 開始日時、curlエラーメッセージ、HTTP 404、HTTP取得失敗、確認処理の終了コード22 | 22 |

各回のcatによるログ表示は終了コード0でした。最終表示には前の2回分を含む3回分が残っており、履歴が追記されていることも確認しました。HTTP確認の失敗1・22を、ログ表示の成功0とは区別しています。

成功時の本文検査は指定文字列の包含です。ログには一致した行が出力され、完全な応答本文を保存する処理ではありません。URLと期待文字列を変えた手動試験で、サーバー障害の発生・復旧や定期監視を検証したわけではありません。

## 理解確認と保存

ログ保存が成功してもHTTP確認失敗時に0を返してはいけない理由について、本人は「HTTP確認の失敗が成功とみなされてしまうから」と説明しました。支援なしの独立再実施は未確認です。
