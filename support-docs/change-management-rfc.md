# 変更管理 / RFC（Request for Change）テンプレートと運用

> **何を / いつ / どう変えるか / 失敗したらどう戻すか** を、変更前に必ず合意するための文書テンプレートです。
> 本ファイルはテンプレート + 実例 1 件を含みます。
> RFC 起票なしの本番変更は、計画外作業として Postmortem 対象になります。

---

## 1. RFC が必要な変更の範囲

| 区分 | 例 | RFC | CAB 承認 |
|------|---|---|---|
| **構成変更** | OS パラメータ、ファイアウォール、DNS、AD ポリシー | 必要 | 必要 |
| **アカウント変更** | 管理者権限付与、共有フォルダ権限変更 | 必要 | 必要 |
| **アプリ更新** | 業務 SaaS 設定変更、Web サーバー設定 | 必要 | 必要 |
| **緊急対応** | 障害復旧での再起動、サービス停止 | **事後** | 翌営業日 |
| **定常業務** | ライセンス棚卸し、退職者削除（手順書通り） | 不要 | — |
| **読み取り操作** | ログ取得、状態確認 | 不要 | — |

CAB = Change Advisory Board（変更諮問委員会）。本Labの想定では「インフラ責任者 + 業務責任者 + 立会観察者」の 3人体制を想定します。

## 2. RFC テンプレート（コピーして使う）

```markdown
# RFC: CR-YYYY-NNN  <タイトル>

## 概要
| 項目 | 内容 |
|------|------|
| RFC番号 | CR-YYYY-NNN |
| 申請者 | <氏名> |
| 起票日 | YYYY-MM-DD |
| 希望実施日 | YYYY-MM-DD HH:MM JST |
| 種別 | [構成変更 / アカウント / アプリ / 緊急] |
| 重要度 | [低 / 中 / 高 / 緊急] |
| ステータス | [Draft / Review / Approved / Scheduled / Done / Rejected] |

## 1. 背景・目的
（なぜこの変更を行うか。3〜5 行）

## 2. 変更内容
（何を、何から何へ変えるか。コマンド / 設定ファイル diff レベル）

```
# 例:
- PasswordAuthentication yes
+ PasswordAuthentication no
```

## 3. 影響範囲
| 影響項目 | 影響内容 | 利用者 |
|----------|----------|--------|
| 対象システム | <例> 全 Linux サーバー 12 台 | 全社 |
| 業務影響 | <例> SSH ログイン手段が鍵のみになる | 運用担当 5名 |
| 周辺サービス | <例> rsync 経由のバックアップは影響なし（鍵運用済） | — |
| ダウンタイム | <例> なし（sshd reload のみ） | — |

## 4. 実施手順（タイムライン）
| 時刻 | 担当 | 操作 | 確認方法 |
|---|---|---|---|
| HH:MM | 申請者 | 事前バックアップ取得 | <hash値の確認方法> |
| HH:MM | 申請者 | Ansible で --check --diff 確認 | 差分出力 |
| HH:MM | 申請者 | 適用 | PLAY RECAP changed 数 |
| HH:MM | 申請者 | 動作確認 | <別経路ログイン成功> |
| HH:MM | 観察者 | 検収サイン | チケットへ |

## 5. ロールバック手順
（失敗時の戻し方。同じ粒度で書く）

| 時刻目安 | 操作 |
|----------|------|
| 失敗検知から 5 分以内 | 旧 sshd_config に Ansible で戻す（git checkout 前回コミット） |
| 5–10 分 | sshd reload, 別経路から鍵+パスワードの両方でログインを試験 |
| 10–15 分 | だめなら IPMI/コンソールから手動修正 |

## 6. 検証項目（完了基準）
- [ ] 鍵での SSH ログインが全 12 台で成功
- [ ] 既知の運用ユーザーで「パスワードログイン」が拒否される
- [ ] PasswordAuthentication が `sshd -T` 出力に no で含まれる
- [ ] 失敗時のロールバック手順が即時実行可能なことを別経路で再確認

## 7. リスクと対策
| リスク | 確率 | 影響 | 対策 |
|---|---|---|---|
| 鍵未配布のユーザーが締め出される | 中 | 高 | 適用前 24h で鍵投入完了を確認 |
| Ansible 適用失敗で sshd 再起動失敗 | 低 | 高 | template に `validate: sshd -t` 設定済 |

## 8. 承認
| 役割 | 氏名 | 承認日 |
|------|------|--------|
| 申請者 | | |
| インフラ責任者 | | |
| 業務責任者 | | |
| 立会観察者 | | |

## 9. 事後記録
- 実施結果: [成功 / 失敗 / 一部失敗 / ロールバック]
- 所要時間: 計画 NN 分 → 実測 NN 分
- 発見した課題:
- 次回への反映:
```

## 3. 実例: CR-2026-014 共有フォルダ VSS 領域拡張

```markdown
# RFC: CR-2026-014  fs01 の VSS 領域を 8% → 15% に拡張

## 概要
| 項目 | 内容 |
|------|------|
| RFC番号 | CR-2026-014 |
| 申請者 | 島田 |
| 起票日 | 2026-04-16 |
| 希望実施日 | 2026-04-22 (火) 19:30 JST |
| 種別 | 構成変更 |
| 重要度 | 中 |
| ステータス | Done |

## 1. 背景・目的
2026-04-15 の DR 演習（dr-test-log #4）で、`\\fs01\share` の VSS 取得世代が
理論値 7 に対して **実測 3 世代** しか保管できていないことを確認。
原因は VSS 領域が共有ボリュームの 8% （初期値）のみであり、世代ローテで
古い世代が押し出されていた。

24h 内で最大 7 世代（3h 間隔）の保管を実現するため、領域を 15% に拡張する。

## 2. 変更内容
```
vssadmin Resize ShadowStorage /For=E: /On=E: /MaxSize=15%
```
- Before: `MaxSize=8%` (480 GB on 6 TB volume)
- After:  `MaxSize=15%` (900 GB on 6 TB volume)

## 3. 影響範囲
| 項目 | 影響 |
|------|------|
| 対象 | fs01 (Windows Server 2022, E: 6TB) |
| 業務影響 | なし（オンライン操作、停止不要） |
| 利用者影響 | 業務時間外実施のため利用者影響なし |
| 容量影響 | E: ドライブの自由領域が 420GB 減少（拡張ぶん） |

## 4. 実施手順
| 時刻 | 担当 | 操作 | 確認方法 |
|---|---|---|---|
| 19:30 | 島田 | 現状の vssadmin list shadowstorage 出力保存 | テキスト保存 |
| 19:32 | 島田 | E: 空き容量が 1TB 以上あることを確認 | `Get-Volume E` |
| 19:34 | 島田 | vssadmin Resize 実行 | コマンド成功確認 |
| 19:35 | 島田 | 再度 list shadowstorage で 15% を確認 | テキスト比較 |
| 19:40 | 観察者 | テスト用ファイルを修正→以前のバージョンから復元 | 復元成功確認 |

## 5. ロールバック手順
```
vssadmin Resize ShadowStorage /For=E: /On=E: /MaxSize=8%
```
- 既存シャドウコピーは保持されるが、超過分は古い世代から削除される

## 6. 検証項目
- [x] vssadmin list shadowstorage が `Used: ... / Allocated: ... / Maximum: 900 GB` を表示
- [x] テストファイルを更新→以前のバージョンから当日 16:00 版を復元成功
- [x] 翌日 06:00 のスケジュール VSS が正常終了
- [x] 翌週 7 世代保持されていることを確認

## 7. リスクと対策
| リスク | 確率 | 影響 | 対策 |
|---|---|---|---|
| E: 空き不足でシャドウコピー削除 | 低 | 中 | 事前に空き 1TB 以上を確認 |
| vssadmin 構文ミス | 低 | 低 | 事前にステージ環境で同コマンド確認 |

## 8. 承認
| 役割 | 氏名 | 承認日 |
|------|------|--------|
| 申請者 | 島田 | 2026-04-16 |
| インフラ責任者 | (任意) | 2026-04-17 |
| 業務責任者 | (任意) | 2026-04-18 |
| 立会観察者 | (任意) | 2026-04-22 |

## 9. 事後記録
- 実施結果: **成功**
- 所要時間: 計画 15 分 → 実測 12 分
- 発見した課題: 特になし
- 次回への反映: 全 FS の VSS 領域基準値を `15%` に統一する標準を作成（fs-vss-baseline.md として別途整備）
```

## 4. 緊急変更（事後 RFC）の運用

緊急対応（障害復旧時の再起動、ホットフィックス）は **先に対応 → 翌営業日に事後 RFC** を起票する運用とします。

- 事後 RFC のフォーマットはテンプレートに準ずる
- ステータスは最初から `Done` で起票し、CAB 承認は事後審査
- 緊急対応中の操作は **`incident-response-playbook.md` のアクションログ** にもタイムスタンプ付きで残す
- 同じ事象が 2 回続いたら必ず Postmortem を起票し、恒久対応を計画 RFC として通常フローに戻す
