# DR / リストア演習記録

> Backup Runbook（`backup-restore-runbook.md`）に書かれている手順が
> **机上ではなく実際に動くこと** を、月次の演習で検証している記録です。
> 演習対象・所要時間・発見した課題を残し、次回の手順改訂の根拠にします。

---

## 演習の基本ルール

| 項目 | 内容 |
|------|------|
| 周期 | **月次（毎月第3水曜 10:00〜12:00）** |
| 演習種別 | A:ファイル単体復元 / B:システム単体復元 / C:DB論理復元 / D:全停止からの再構築 を **3ヶ月で1巡** |
| 参加者 | 一次担当 + バックアップ責任者 + 立会観察者 1名 |
| 環境 | 本番ではなく **隔離Lab VM** で実施。同OS / 同バージョン / 同手順で再現する |
| 完了基準 | ① Runbook 通りに完走 ② RTO 内に復旧 ③ データ差分 0（または許容差分内） |
| 中断基準 | 30分 経過時点で進捗 50% 未満なら **演習中断 → 障害シナリオとして起票** |
| 記録 | この `dr-test-log.md` に追記 / Postmortem 形式で課題を起票 |

### 目標値（Backup Runbook と整合）

| 対象 | RPO (許容データ損失) | RTO (許容停止時間) | 実測（直近） |
|------|----------|----------|----------|
| 共有ファイルサーバー（Win VSS） | 24h | 4h | 1h 12m |
| Web/App サーバー（Linux rsync） | 24h | 2h | 38m |
| 業務DB（mysqldump 日次 + binlog） | 1h | 2h | 1h 04m |
| AD DS（System State + IFM） | 24h | 4h | 2h 18m |

## 演習記録

### 2026-05-20（水）演習 #5: B - Linux Web サーバー単体復元

| 項目 | 内容 |
|------|------|
| 対象 | `web-app01` (Ubuntu 22.04 / Nginx + PHP-FPM + 静的コンテンツ 18GB) |
| シナリオ | 「OS ディスク破損で起動不能になった想定」での bare-metal 復旧 |
| 演習方法 | Lab に同サイズ VM を新規払い出し → rsync バックアップ先からリストア |
| 開始 | 10:02 / 終了 11:00 / **所要 58分** |
| RTO 達成 | ✅（目標 2h / 実測 58m） |
| RPO 達成 | ✅（前夜 03:00 のバックアップから復元 / 業務影響なし時間帯） |

**所要時間の内訳**

| ステップ | 計画 | 実測 | 備考 |
|---|---|---|---|
| 1. Lab VM 新規払い出し（同スペック） | 10m | 8m | Terraform で雛形化済 |
| 2. SSH 鍵投入 + Ansible baseline 適用 | 15m | 14m | `--tags ssh,firewall` のみ |
| 3. `/etc` / `/var/www` を rsync で復元 | 30m | 22m | `--link-dest` で差分のみ |
| 4. systemd ユニット再有効化 + 設定整合確認 | 15m | 9m | `daily-backup.timer` も復旧確認 |
| 5. Nginx 起動確認 + 動作テスト（curl） | 10m | 5m | `/healthz` 200 + HTML 内容一致 |

**発見した課題**

1. `/var/www/uploads` 配下に **rsync excludes に書き忘れたキャッシュディレクトリ** があり 4GB 余計に転送していた。
   → `backup-restore-runbook.md` の rsync excludes に `uploads/cache/` を追記（次回確認）。
2. systemd timer 復旧後、`OnCalendar` の解釈に **TZ ずれが 9時間** あった。
   → `/etc/timezone` を Ansible 適用前に確認する手順を Runbook L82 に追加。
3. curl 動作確認で **TLS 証明書だけ別途復元が必要** だった（/etc/letsencrypt が rsync 対象外）。
   → 次回演習で `/etc/letsencrypt` を rsync 対象に含める修正版で再検証する。

**ステータス**: ✅ 完了 / 課題3件を次回演習までに反映

### 2026-04-15（水）演習 #4: A - ファイル単体復元（共有フォルダ Win VSS）

| 項目 | 内容 |
|------|------|
| 対象 | `fs01` 共有フォルダの `\\fs01\share\営業\2026Q1.xlsx` 1ファイル |
| シナリオ | 「誤って上書き保存してしまった」想定 |
| 演習方法 | VSS（シャドウコピー）から右クリック→以前のバージョン→ローカル保存 |
| 開始 | 10:08 / 終了 10:19 / **所要 11分** |
| RTO 達成 | ✅（目標 4h / 実測 11m） |
| RPO 達成 | ✅（VSS 取得時刻 当日 06:00、想定通り） |

**発見した課題**

- VSS 領域が共有ボリュームの **8% しか確保されていなかった** ため、24h 内の保管世代が想定より少ない（理論値 7 → 実測 3）。
  → `shadowstorage` を 15% に変更する変更管理（RFC）を起票（CR-2026-014）。

**ステータス**: ✅ 完了 / RFC CR-2026-014 で恒久対応

### 2026-03-18（水）演習 #3: D - 全停止からの再構築（縮退）

| 項目 | 内容 |
|------|------|
| 対象 | Lab の最小構成（FS + DB + Web の 3VM） |
| シナリオ | データセンター全停止 → 別拠点 / クラウドへ縮退立ち上げ |
| 演習方法 | Azure 上に Terraform で 3VM 払い出し → バックアップから復元 |
| 開始 | 10:00 / 終了 12:00 で **中断（進捗 75%）** |
| RTO 達成 | ❌（DB の binlog 適用で詰まり時間切れ） |

**発見した課題（重大 1 / 警告 2）**

1. **重大**: binlog のオフサイト転送が **1日 1回 03:00 のみ** で、直近 8 時間分が手元になく、PIT 復旧不能。
   → 即時改修。`mysqldump` 日次 + `binlog` 15分間隔 S3 同期に変更（CR-2026-009、完了済）。
2. **警告**: Terraform の variables.tf に **VM サイズが本番より小さい値** がハードコードされていた。
   → DR時のサイズ切替変数を追加（PR #214 で対応済）。
3. **警告**: 復旧手順書の SSH 鍵パス記述が古く、鍵投入で 12分ロス。
   → Runbook 修正済。次回再演習を予定。

**ステータス**: ⚠️ 中断 / 重大1件は対応完了、再演習を 2026-06 に設定済

**学び**:
- 「Runbook 通りに動かす演習」を月次で継続することで、Runbook 自体の **腐敗（手順と実装のズレ）** を早期発見できている。
- 全停止演習（D）は半年に 1 回でも、**RPO の盲点（オフサイト転送頻度）を必ず炙り出す**。
- 演習で見つかった課題は必ず RFC または Runbook 修正に紐付けて、**口頭で終わらせない** ようにしている。
