# SIer / MSP / クラウドベンダー一次受 向け追記

「**システムインテグレーター (SIer)、マネージドサービスプロバイダ (MSP)、クラウドベンダーの一次受け / 二次対応**」ポジションを志望する場合の本ポートフォリオの読み方と、口頭補足のポイントです。

SIer / MSP は「**顧客への報告書 / エビデンス文化**」「**承認フロー / 変更管理の重さ**」「**マルチテナント運用**」「**手順化と再現性**」に特徴があります。

---

## SIer / MSP が重視する 6 つの観点

| # | 観点 | 理由 |
|---|---|---|
| 1 | **手順書 + チェックリスト文化** | 顧客環境に勝手な判断を入れない。手順書 100% 準拠 |
| 2 | **証跡保存 + 報告書** | 全作業はチケット記録 + スクリーンショット + 月次レポート化 |
| 3 | **承認フロー (CAB) の遵守** | 変更管理委員会 (CAB) 通過なしの作業は基本禁止 |
| 4 | **マルチテナント** | 複数顧客環境を扱う。設定間違いが横展開しないこと |
| 5 | **クラウド資格 (AWS / Azure / GCP)** | 顧客への提案 / 設計 / 構築 / 運用の各フェーズで資格要求 |
| 6 | **シフト / オンコール / 24h 体制** | NOC 運用 / 一次受け 24h / 二次対応のローテーション |

## SIer / MSP 特化で追加で言及する点

### 1. 「顧客環境に勝手なことをしない」感覚

製造・物流 18 年で「**現場のルールは現場のルール**」という感覚を肌で持っています。SIer / MSP の現場でも、

- 顧客環境への作業は**手順書 100% 準拠**、判断が必要なら一次受けで止めて二次へエスカレ
- 「自分なら違う設計」と思っても、顧客の意思決定を尊重し、**改善は提案ベース**で
- 過去の引き継ぎ資料を最初に読み、**現状把握 → 改善案 → 提案 → 合意 → 実行**のサイクルを守る

を意識します。本ポートフォリオの[チケット分類](../ticket-taxonomy.md) で「**判断に迷う典型例**」を例示しているのは、この感覚の表れです。

### 2. 顧客報告書として使えるドキュメント

本ポートフォリオの

- [Postmortem 実例](../postmortem-example.md) → そのまま顧客向け事後報告書のテンプレートに転用可能
- [Backup Runbook](../backup-restore-runbook.md) → そのまま顧客向け運用設計書として提出可能
- [SLO ドキュメント](../slo-error-budget.md) → 顧客向けサービス品質報告に転用

を、社内資料ではなく**顧客提出物の品質で書いている**点を強調できます。実際、顧客に出してもギャップが小さい品質を目指しました。

### 3. クラウド資格との連動

本ポートフォリオで触れている AWS は VPC / Subnet / SG / Terraform validate までで、課金を伴う `apply` 経験はありません。

- 入社後の最優先資格として **AWS SAA / AZ-104** を計画
- 既に Terraform でリソース定義は読み書きできる前提なので、**手を動かす速度**は早い想定
- 資格と実機経験のギャップは入社後 3 ヶ月で埋める計画を明示

### 4. ITIL の意識

本ポートフォリオの[チケット分類](../ticket-taxonomy.md)は ITIL 4 の Service Management Practices をベースにしています。SIer / MSP では ITIL の理解が前提として求められることが多く、

- インシデント / サービスリクエスト / 問題 / 変更 の 4 区分を明確に分離
- 標準変更 / 通常変更 / 緊急変更の 3 段階で CAB 通過の有無を明示
- 真因分析 (Problem Management) は 5 Whys で記述

を理解した上で運用できる状態を示せます。

### 5. 製造業 18 年の現場感

製造・物流現場で 18 年やってきたので、

- **顧客の業務影響**を技術用語ではなく業務用語で表現できる
- **現場が止まる怖さ**を肌で知っている
- 「**技術的に正しい**」より「**業務として安全**」を優先する判断軸

を持っています。SIer の一次受けは現場ヒアリングが多いため、この経験が活きると考えています。

## 入社後 3 ヶ月の進め方 (SIer / MSP 想定)

| 期間 | 目標 | 具体物 |
|---|---|---|
| 1 週目 | アサインされた顧客環境のドキュメント通読 + 主要関係者の把握 | 引き継ぎサマリー / 関係者図 |
| 2-4 週目 | 監視ダッシュボード / アラート / 既存チケット 100 件を読み、よくあるパターンを把握 | 「よく起きる事象 TOP 10」自分用メモ |
| 2 ヶ月目 | 一次受けを副担当として実施 (シニアの隣で同じチケットを処理) | 自分が処理したチケット 30 件のサマリー |
| 3 ヶ月目 | 軽微な変更作業を主担当 + 月次報告書を一部担当 | CAB 提出書類 1 件 + 月次レポート 1 章 |

## 補強したい技術 (応募までに / 入社後に)

| 領域 | 状態 | 補強計画 |
|---|---|---|
| **AWS / Azure / GCP** | AWS Lab レベル (VPC / Terraform validate) | AWS SAA (2026Q4) → AZ-104 (2027Q1) |
| **ITIL** | 概念理解 + チケット分類フロー実装 | ITIL 4 Foundation 受験予定 |
| **ServiceNow / JIRA** | 未経験 | フリーアカウントで Lab、API 連携検証 |
| **VMware vSphere / Hyper-V** | Hyper-V 基本のみ | 検証 VM で複数台 / vMotion 観点 |
| **シェル / PowerShell スクリプト** | 9 本 + Pester 25 テスト | より深い PSScriptAnalyzer ルール対応、ShellCheck |
| **資格** | ITパスポート (2026-06) | ITIL 4 → AWS SAA → CCNA |
