# 案件14追加：nginx停止からの復旧演習

実施日：2026年9月14日（JST）

本人がWSL Ubuntu上の練習用nginxを意図的に停止し、接続失敗を確認した後、起動して初期ページを再取得しました。AIが手順を案内し、本人が提示した端末画面を読み取って公開用要約を作成しています。AIによる代理実行やCIの結果ではありません。

[9月11日の案件14](./cli-practice-2026-09-11.md)は総合調査までで、停止・復旧試験は未実施でした。本書はその後の追加実施です。過去の日付の記録を、当時から復旧試験済みだったようには変更しません。

## 対象と事前確認

- 対象は本人専用のWSL内のnginxと、同じWSL内からのHTTP接続です。
- 本人が短時間停止しても問題ないと確認してから実施しました。
- 停止前にHTTP 200、本文の`Welcome to nginx!`、curl終了コード0を確認しました。サービス状態確認の終了コードも0でした。
- 操作はサービスのstopとstartです。設定ファイルの変更、OSの再起動、データ復元は行っていません。
- 公開時の文書基点は`37b87be`です。実際のnginx設定やパッケージをこのcommitで管理していたという意味ではありません。今回、nginxの版は再取得していません。

## 本人が実施した操作と結果

| 段階 | 操作・確認 | 提示画面で確認した結果 |
| --- | --- | --- |
| 正常時 | 同じWSL内からcurlで初期ページを取得 | HTTP 200、期待する本文、終了コード0 |
| 停止 | `sudo systemctl stop nginx` | 停止の終了コード0 |
| 停止状態 | `systemctl is-active nginx` | inactive、終了コード3 |
| 接続失敗 | 最大5秒のcurlでHTTP接続 | Failed to connect、終了コード7、HTTP表示000 |
| 復旧 | `sudo systemctl start nginx` | 本人が実行。起動コマンド自体の終了コードは提示画像では見切れており未確認 |
| 稼働確認 | `systemctl is-active nginx` | active、終了コード0 |
| ページ再取得 | 最大10秒のcurlでHTTP応答と本文を確認 | HTTP 200、Welcome to nginx!、復旧確認の終了コード0 |
| 記録保存 | WSL内に演習記録を保存し、catで再表示 | 保存の終了コード0と記録内容を確認 |

接続失敗時の000はサーバーが返したHTTPステータスではなく、curlがHTTP応答を受け取れなかったときの表示です。停止状態の確認コマンドの終了コード3と、接続確認の終了コード7を、停止操作そのものの失敗とは扱いません。

起動コマンドの終了コードが画面で見切れている点は残しつつ、その後のactive・HTTP 200・期待する本文を復旧確認の根拠とします。

## 時刻と判断の範囲

停止操作前の`date -Is`は10:18:37 JST、HTTP復旧確認後は10:20:36 JSTでした。両時刻の間にはパスワード入力や結果の共有・手順確認が含まれるため、差を正確なサービス停止時間やRTOとして扱いません。

今回確認したのは「正常応答 → 意図的な停止で接続失敗 → 起動後に正常応答」です。自然発生した障害の原因究明や、異常終了からの復旧を実施したという意味ではありません。

本人は理解確認で「アプリが稼働したからと言って、ページ取得できているとは限らない」と説明しました。サービス状態だけで終えず、HTTP応答と期待する本文まで確認する理由を説明できました。
