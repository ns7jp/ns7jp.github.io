# SLO / SLI / エラーバジェット定義書

> 監視対象サービスごとに **「どこから NG とみなすか」「どの程度の劣化を許容するか」**
> を文書化したものです。Prometheus アラートのしきい値（`alert.rules.yml`）の根拠と、
> 一次対応・引き継ぎ判断（`infra-lab.html` の Monitoring & Evidence Matrix）の判断軸になります。

## 用語の前提

| 用語 | 内容 |
|------|------|
| **SLI** (Service Level Indicator) | 「現状の良さ」を表す測定可能な指標。例: 5xx 比率 / レイテンシ p95 |
| **SLO** (Service Level Objective) | SLI に対する目標値。「30 日間の 5xx 比率 0.5% 以下」など |
| **エラーバジェット** | 100% - SLO。これを使い切ったら新機能投入を止め、安定化に振る |
| **アラートしきい値** | エラーバジェットの **燃焼速度** から逆算（速い燃焼ほど低い `for` 時間） |

エラーバジェットは「許容される失敗の枠」と捉え、**0% を目指さない** ことが大切です。
0%を目指すと変更を止めることに繋がり、結果として可用性が落ちます。

## 監視対象サービスと SLO

### 1. 社内ファイルサーバー (SMB/CIFS)

| 項目 | 内容 |
|------|------|
| サービスタイプ | 業務支援（社内のみ） |
| 利用者 | 全社 約 200 名 |
| 業務時間 | 平日 08:00–20:00 |
| **SLI 1** | 業務時間内の SMB セッション応答成功率 |
| **SLI 2** | 業務時間内のディスク I/O p95 < 200ms |
| **SLO 1** | 月次 99.5%（業務時間ベース 30日 = 360h、停止許容 1h 48m） |
| **SLO 2** | 月次 95%（200ms 超過は 5% まで許容） |
| **エラーバジェット** | 0.5% × 360h = **108 分 / 月** |
| 関連アラート | `HostLowDisk` (空き<10%), `HostHighIO` (await>50ms 10m) |
| 引き継ぎ判断 | 月の途中で 60分 (= 予算の 55%) 消費した時点で **変更凍結 + 容量・I/O 棚卸し** |

### 2. 社内 Web/App サーバー（業務システム）

| 項目 | 内容 |
|------|------|
| サービスタイプ | 業務支援（社内のみ、リバプロ越し） |
| 利用者 | 全社 約 200 名（ピーク 同時 50） |
| **SLI 1** | リクエスト成功率（HTTP 2xx + 3xx 比率） |
| **SLI 2** | レイテンシ p95 |
| **SLO 1** | 月次 99.9%（5xx 比率 0.1% 以下） |
| **SLO 2** | レイテンシ p95 < 800ms（30日の 95%時間で達成） |
| **エラーバジェット** | 0.1% × (リクエスト総数) |
| 関連アラート | `Http5xxRate` (5xx > 1% 5m), `LatencyP95High` (p95>1.5s 10m) |
| 引き継ぎ判断 | 5xx > 1% が 5分継続 → ただちに一次対応（再起動禁止、まず証跡） |

### 3. Active Directory / DNS

| 項目 | 内容 |
|------|------|
| サービスタイプ | 基盤（全業務の前提） |
| 利用者 | 全社・全端末 |
| **SLI 1** | 認証成功率（LDAP bind 成功 / 全試行） |
| **SLI 2** | DNS クエリ応答 p95 < 50ms |
| **SLO 1** | 月次 99.95%（停止許容 21分 / 月） |
| **SLO 2** | 月次 99%（50ms 超過は 1% まで） |
| **エラーバジェット** | 0.05% × 30日 = **21 分 / 月** |
| 関連アラート | `LdapBindFail` (失敗率>0.5% 2m), `DnsLatencyHigh` (p95>100ms 5m) |
| 引き継ぎ判断 | 認証停止は **即時** P1 起票。DNS は二重化のうち 1台 ダウンで P2 |

### 4. 社外向け Web サイト（ポートフォリオ含む）

| 項目 | 内容 |
|------|------|
| サービスタイプ | 情報公開（収益直結ではない） |
| 利用者 | 不特定多数 |
| **SLI 1** | 外形監視（公開URL の HTTP 200 返却率） |
| **SLI 2** | TTFB |
| **SLO 1** | 月次 99%（停止許容 7h 12m / 月） |
| **SLO 2** | TTFB p95 < 1500ms |
| **エラーバジェット** | 1% × 30日 = **7h 12m / 月** |
| 関連アラート | `BlackboxDown` (probe_success=0 5m), `TtfbHigh` (p95>2s 10m) |
| 引き継ぎ判断 | バジェット 50% 消費で原因分析、80% でリスクレビュー、超過で凍結 |

## しきい値の根拠

`monitoring-stack/prometheus/alert.rules.yml` のしきい値は、上記 SLO から逆算しています。

| ルール | しきい値 | for | 根拠 |
|---|---|---|---|
| `HostHighCpu` | > 85% | 10m | 一過性のジョブで超えやすいため for を 10m。85% は AD/Web の応答劣化が始まる経験値 |
| `HostHighMemory` | available < 10% | 15m | OOM Killer 発火直前の余裕値。15m は GC やバッチで一時的に上がる影響を吸収 |
| `HostLowDisk` | 空き < 10% | 10m | logrotate 1サイクル内に検知できる短さ。Critical 即対応 |
| `NodeExporterDown` | up == 0 | 5m | 単発スクレイプ失敗（ネットワーク瞬断）を排除する最小値 |

**新規アラートを追加するときの手順**

1. 対象サービスを上の SLO 表に追記
2. SLI を Prometheus で取得できる式に書き下す
3. しきい値と `for` を SLO から逆算（バジェット燃焼速度を計算）
4. `alert.rules.yml` に追加し、`promtool check rules` で構文確認
5. 抑制（silence）対象になるラベル設計を決め、Alertmanager の routing と合わせる
6. 30日運用してチューニングし、誤検知率 5% 以下を目指す

## エラーバジェット運用

| バジェット消費率 | アクション |
|------------------|------------|
| 0–50% | 通常運用。新機能投入・変更を継続 |
| 50–80% | レビュー強化。リスクが高い変更は次月送り |
| 80–100% | 変更凍結。安定化作業のみ |
| 100% 超過 | **本番変更停止**。Postmortem 必須。次月までに恒久対応 |

> 凍結判断は技術的判断と同時に **業務判断** が絡みます。SLO は「経営側と運用側が合意した数値」であるべきで、
> 運用側だけで決めると形骸化します。本書は将来この合意を行うためのたたき台として置いています。
